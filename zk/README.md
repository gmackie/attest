# Native ZK proof-of-concept for $ATTEST (single claim, Sepolia only)

**Experimental; no production launch, no live token deployment, no real money.
The build produces a deliberately INSECURE Groth16 trusted setup. NEVER use
its `*.zkey` or verifier for valuable assets.**

This second milestone adds a direct on-chain path for minting $ATTEST. The
earlier private POD/GPC proof + trusted EIP-712 authorization remains available
separately. This circuit is **not** a POD signature verifier: its authenticated
claim format is an issuer-published Poseidon commitment inside an on-chain
issuer-managed current Merkle root. Mapping a POD credential to this new
issuer-signed/root-issued claim requires the issuer's own reliable issuance
process and holder/subject binding; the protocol does NOT automatically treat
any private credential as an eligible mint.

## What the circuit proves

A holder privately knows:
- an issuer-assigned, high-entropy canonical `eventSecret`;
- a private `holderSecret` committed by the issuer;
- a bounded score (700–10,000) and expiration;
- four sibling hashes and left/right bits proving leaf inclusion in a
  16-leaf Poseidon commitment tree;

whose leaf was `Poseidon(eventSecret, holderSecret, score, validUntil,
issuerAddress)`. The proof establishes a live issuer root, and derives:

- `nullifier = Poseidon(eventSecret, 81501)` (stable across recipient,
  policy, proof challenge, root versions, and verifier addresses);
- `provenance = Poseidon(eventSecret, 81502)`;

while constraining public `policyId=1`, `chainId=11155111`,
`amount=200e18`, a four-channel `palette`, valid timestamps and bounded
addresses. The zero-knowledge proof does not reveal score, event ID, holder
secret, or Merkle path. Issuer root, issuer address, recipient, expiry,
amount, palette, nullifier and provenance commitment are public.

The Solidity `ZkAttestMinterV1` additionally checks live, authorized
`PrivateClaimRoots` state, token address, chain, exact policy and payouts,
expiration, and the Groth16 proof; it then calls the existing test ERC-20's
`mintFromZk` which **atomically consumes** the same `spentNullifiers` map
used by legacy signed vouchers. This avoids replay between mint paths.

### Authentication and revocation boundary

`PrivateClaimRoots` relies on the administrator to approve real issuer
addresses; each approved issuer (authenticated by Ethereum transaction
signature) must build and publish an active Poseidon root over credentials it
stands behind. Issuers revoke events by rebuilding/removing leaves and
replacing the root. A proof for an outdated root fails at mint time.

The circuit establishes **membership in that issuer's published root**, not
independent real-world truth, credentials' historical issuer authority,
legal identity, compliance, physical outcomes or integrity of the issuer's
off-chain data source. Issuers can publish bad roots. An admin can install
an attacker minter or root authority; those powers require governance.
There is no ZK guarantee of canonical event IDs across unaffiliated
issuers. Correct event ID deduplication requires issuance governance and
external evidence policy, not just hashes.

**Experimental limitations:**
- exactly **one** eligible event per proof; policy amount and palette are
  hard-coded, not arbitrary private weighted multi-claim arithmetic;
- capacity fixed at a depth-4, 16-leaf tree (the issuer's active root is
  replaced, not incrementally governed);
- the token and root contracts are bespoke proof-of-concept implementations;
- one EOA administrator, no contract upgrade/recovery, no independent audit;
- circuit `eventSecret` is random and stored privately by issuer and holder;
- no interactive browser proving UI in this milestone; proof is currently
  generated by test scripts in a native build environment;
- public nullifier and provenance are deterministic and can correlate a
  rare event if the underlying secret is guessed;
- issuer-status root updates are immediate on-chain but do not prove physical
  credential freshness, cross-chain finality or real-world revocation;
- trusted-setup artifacts here are ephemeral, unreviewed and **insecure**.
  No immutable or vetted verification key has been deployed.

## Local test-only build

Use Node 24 and pnpm 10, Anvil, plus a temporary isolated toolchain:

```bash
pnpm install --frozen-lockfile
mkdir -p /tmp/attest-zk-toolchain
npm install --prefix /tmp/attest-zk-toolchain --no-save --no-package-lock \
  circom2@0.2.23 circomlib@2.0.5 circomlibjs@0.1.7 snarkjs@0.7.5
node zk/scripts/build-test-fixture.mjs
pnpm --filter @attest/contracts build
node contracts/scripts/compile-zk.mjs
pnpm exec vitest run zk/tests/onchain.test.ts
```

The generated verification key, Solidity verifier, circuit wasm, and zkey are
intentionally excluded from Git history under `zk/.generated/`. CI repeats
the full synthetic setup. Artifacts are pinned by compiler/package versions
but the deliberately ephemeral unsafe ceremony is **not** a usable mainnet
setup or an audited, deployed verifier.

## Test cases

Anvil deploys the token, issuer-root registry, generated Groth16 verifier,
and native minter. The integration test constructs a private witness, proves
it with real Circom/Groth16, confirms `snarkjs` verification, and mints on
the simulated Sepolia chain. Negative calls mutate recipient, chain,
token, amount, palette, policy, nullifier and provenance; old roots,
unauthorized publishers, revoked issuers, pause states and replayed
nullifiers must fail. Token supply and observed gas are checked.

## Before it can be production-ready

- A **real, multi-party production ceremony** or reviewed alternative proving
  scheme; checked-in verification-key hash and independent artifact audits.
- Adapt current private POD/VC claim schema into an authority-checked,
  issuer-maintained commitment tree with explicit identity/subject proofs.
- Multi-claim composition: distinct-event handling, arithmetic constrained
  in-circuit, cross-issuer canonical event rules and emissions/governance.
- Security review and circuit audit; fuzzing and arithmetic/field bounds,
  conditional privacy protection, protections against threshold inference,
  subject recovery, key lifecycle, temporal status/finality, governance,
  regulator and consumer disclosure review.
- A private prover UI with custody, staged proving and resource limits;
  deployment runbooks with verified Sepolia deployments, not untrusted
  generated test fixtures.
