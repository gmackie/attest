Attest on-chain trust stack: roadmap with Gatekeeper and Nathan Proposal

2026-11-21 · attest @ main 0a31db6 · gatekeeper @ origin/main · nathan @ feat/NATH-8-login-recovery-hardening 04e1525 · covers the demo, pilot and agent-commerce goals together

Recommendation: Build one shared loop: Gatekeeper asks for a proof the way it already asks for MFA, Attest answers privately, and the chain records verifiable status and receipts. Ship it in four phases.

  • Phase 0: agree the interfaces between the three projects.
  • Phase 1: the "prove-to-access" demo, which doubles as the pilot design.
  • Phase 2: agent commerce, with mandate limits enforced on-chain.
  • Phase 3: pilot and mainnet hardening.

The demo, the pilot and agent commerce all reuse the same verifier, status reader and receipt log, so building that core once serves all three goals.

Correction to the earlier brainstorm: Nathan's latest commit cancels RBAC (NATH-13): "Nathan is authentication only; authorization belongs to Gatekeeper". So "roles earned from proofs" lives in Gatekeeper. Nathan contributes only authenticated identity, plus optional wallet sign-in.

The stack: one question per layer

Nathanauthentication
Who is calling? A Better Auth IdP on Workers. Issues the subject sub plus Gatekeeper-ready access tokens (NATH-15: RFC 9068, principal_kind, ≤900 s). It will gain per-scope agent consent (NATH-14). It holds no roles or policy.
Attestassurance
What can they prove, and who vouches for it? Private POD/GPC presentations, scoped issuer authority, and signed agent mandates. Raw evidence never leaves the holder.
Gatekeeperauthorization
May they do this, now? An OPA/Rego PDP with PIPs (policy information points), allow/deny/challenge outcomes, mandate budget reservations in D1, and an MCP gateway.
Chainpublic record
What anyone can check later. Issuer grants, revocation status, decision-log roots, and limits enforced on-chain. Commitments only, never evidence.

The chain is the missing link today. Attest writes to Sepolia, but none of the three projects reads that state when making a decision. Gatekeeper mandate status comes from a local demo_credentials table (apps/operations/service.ts:77-82), and attest verifiers expect callers to supply issuer keys and records (packages/proofs/src/criteria.ts:99).

Core idea: the proof challenge

Gatekeeper's precedence already returns challenge when MFA or approval is missing (policies/gatekeeper.rego:118-132). Add a third challengeable requirement: an attest presentation. The client handles it the same way as step-up MFA.

  1. Nathan User or agent signs in and gets an access token (aud = Gatekeeper resource).
  2. Gatekeeper POST /api/authorize for vendor.payout.approve. The policy requires attest_presentation: insurance.cgl.min-2m.
  3. Gatekeeper → challenge with a signed proof request. The request binds the decision ID, Nathan iss/sub, audience, requirement ID, nonce and expiry. This also closes the "unsigned request" gap in attest's production-readiness review.
  4. Attest wallet Holder generates the GPC proof locally. The verifier learns only "requirement met", not the $5M figure.
  5. Attest verifier Checks the proof, issuer authority, request binding and chain status at a finalized block, then returns a short-lived signed result.
  6. Gatekeeper PIP accepts the result as a fact with a freshness bound, then re-evaluates → allow.
  7. Chain The decision goes into a hash-chained log. The Merkle root is anchored periodically, and anyone can get an inclusion proof for their receipt.

Options for sequencing

A. Shared core first Recommended

  • Phases 0 and 1 deliver the demo and the pilot architecture.
  • Agent commerce reuses the verifier, status reader and receipt log.
  • Builds on the real Gatekeeper extension points listed below.
  • Cost: the agent-payments wow comes later (Phase 2).

B. Agent commerce first

  • Most novel and investable story.
  • Depends on smart accounts, stablecoins, the Gatekeeper co-signer and NATH-14 at once.
  • Without the status reader and verifier, limits stay off-chain anyway.

C. Mainnet hardening first

  • Required before any real issuer writes.
  • Produces little to show.
  • Risks hardening contracts before the integration shape is known.

Goals and non-goals

Goals

  • Chain state that a live decision path actually reads (status, grants, limits)
  • One end-to-end demo across Nathan, Gatekeeper and Attest on testnet
  • A pilot-ready design: signed requests, finality policy, key rotation
  • Agents spend within signed mandates, with limits enforced on-chain
  • Tamper-evident, privacy-preserving decision receipts

Non-goals (this roadmap)

  • Raw evidence, exact values or identity on-chain (AGENTS.md)
  • Expanding the $ATTEST token beyond Sepolia research (AT-02/03/07 are open)
  • Roles or policy inside Nathan (NATH-13 cancelled)
  • Claiming production ZK: POD/GPC is beta and unaudited, and the circuit setup is unsafe
  • Ethereum L1 mainnet writes before the release dossier passes

Mitigations
  • R1: Keep AGENTS.md wording. Label the step-1 attribute path "verified off-chain, freshness-bounded". Never call a policy match a proof, and keep "beta, unaudited" on GPC.
  • R2: Testnet stablecoin only. Fuzz and invariant tests on caps. Gatekeeper co-signature plus a pause guardian. External audit before any mainnet value.
  • R3: Phase 1 can use today's Nathan JWTs through Gatekeeper's marker-claim profile (fixtures/identity-providers.example.json) as a stopgap. Swap to NATH-15 once it lands.
  • R4: Batch decision roots, salted leaves, pairwise holder keys. Never anchor per-decision events.
  • R5: Leave $ATTEST out of this roadmap. Phase 2 uses an existing test stablecoin.
  • R6: Pin @pcd/gpc 0.4.1 and the artifact hashes. Fail closed on mismatch.

Verification

  • A cross-repo end-to-end test (Nathan token → Gatekeeper challenge → Attest proof → allow → inclusion proof) runs in CI on testnet or anvil fixtures.
  • Every new verifier and contract ships the AGENTS.md negative joins: mismatched subject, stale, unauthorized issuer, duplicate, insufficient hidden value. Add replay, reorg and audience-swap tests as well.
  • The demo is checked with a /browse QA pass. Production steps follow the ForgeGraph delivery evidence rules, with Kanbanger issues per project.

Open decisions

1. Pilot domain and partner

Who is the first real issuer and verifier?

Contractor insurance (the existing domain pack) is the fastest. Healthcare and education add regulatory weight.

2. Production network

Base, OP or Ethereum L1?

Recommend an L2 for receipts and limits. Revisit L1 only for registry roots.

3. Who runs the verifier?

An attest-hosted service, or embedded in Gatekeeper?

Recommend an attest Worker that Gatekeeper calls via a service binding. It keeps the protocol kernel chain- and vendor-neutral.

4. Wallet sign-in in Nathan

Add SIWE as an auth method?

Optional. The proof challenge binds holder to subject without it. It is useful for Phase 2 smart-account ownership.
